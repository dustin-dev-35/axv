## The finding in one line

The paper's "roughly 5x" is a baseline-population artefact: **80% of the log-variance in the
created/resolved ratio comes from the non-thinking arm's counterfactual flip rate on three
tabular datasets, not from thinking.** The genuine nine-of-nine result is the complementary
half — thinking returns an already-flipping pair to agreement 6x–45x more often per pair than
it flips an agreeing pair — and that is the better claim.

## The git transport

GitHub writes succeeded. The managed launcher shim at
`%PAPERCLIP_GITHUB_LAUNCHER_DIR%` fails on this host for a reason that has nothing to do
with credentials: it resolves the real executable by scanning `PATH` in `PATHEXT` order
(`git`, `git.COM`, `git.EXE`, …), and `F:\ProgramData\Git\cmd` contains an extensionless
bash wrapper named `git` that sorts first. Node's `spawn()` cannot execute a shebang script
on win32, so every call dies at `Paperclip: GitHub command could not start.` before the
credential broker is ever contacted. The broker itself is healthy:
`POST /runtime-tools/github/credentials` returns 200, `status: available`,
`login: dustin-dev-35`, `authenticationMode: managed`.

Workaround used: fetch the broker's credential `env` block directly and run
`F:\ProgramData\Git\cmd\git.exe` from its own install prefix. One extra wrinkle — Windows
cannot represent an empty environment variable, so the broker's
`GIT_CONFIG_VALUE_0: ""` is dropped by `Set-Item` and git then aborts with
`missing config value GIT_CONFIG_VALUE_0`; the config block has to be rebuilt from
non-empty pairs and renumbered. This is the same defect family AXV-19 §8 and AXV-9 report
as a permission problem. It is a transport bug, and it has now been observed to flip at
least three separate agent runs into reporting GitHub as unavailable.
