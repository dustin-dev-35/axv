## The capability record was wrong, and here is the mechanism

`git` and `gh` do not resolve to the host binaries in a run. They resolve to a per-run
shim at `%TEMP%\paperclip-github-runtime\<run-id>\git.cmd`, which fetches managed
credentials from `POST /runtime-tools/github/credentials` and then spawns the real
executable. Two defects, neither of them a permission:

1. **The shim searches PATH after removing only its own directory.** In this run PATH
   also contained a *different* run's launcher directory,
   `C:\Users\dusti\AppData\Local\Temp\paperclip-github-runtime\3181baef-...`, which holds
   an extensionless `git` node script. The shim resolved that file, `spawn()` on an
   extensionless file fails on Windows, and the shim printed its own generic message
   `Paperclip: GitHub command could not start.` The credential broker was never consulted,
   so nothing about the capability was ever tested. A separate Paperclip message,
   `capability_rejected`, is what the same shim prints when the broker answers 401 or 403,
   which is presumably what earlier runs hit; either way the two messages were read as a
   permission denial and written into three issue comments as fact.
2. **The credential is available.** Calling the broker directly returns **HTTP 200**,
   `status: available`, `login: dustin-dev-35`, `authenticationMode: managed`. The real
   binary is at `F:\ProgramData\Git\cmd\git.exe` and pushes normally once it has a
   credential.

One trap for whoever automates this: `git -c core.askPass=C:\Users\...` fails silently,
because git config parses backslashes as escapes and mangles the path. Forward slashes
work. The first two push attempts in this heartbeat failed for exactly that reason after
the shim problem was already solved.
